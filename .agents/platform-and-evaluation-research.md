# Platform and evaluation research

Verification date: **2026-10-09**. Sources: current official documentation fetched during this research. Documentation observations below are distinct from proposed RecallHQ decisions. No authenticated API behavior was tested; actual grants, plan, installation classification, retention and SDK versions remain deployment-specific. No reference code or Jev research was performed; no code, dependencies or network accounts were changed.

## Observed documentation: Slack

- **History/replies limits:** Both methods document **1 request/minute and 15 objects maximum/default** for new commercially distributed apps/installations outside Slack Marketplace, effective May 29, 2025. Marketplace and internal customer-built apps retain Tier 3 (**50+ requests/minute**). Current pages explicitly exempt existing non-Marketplace installations; do not assume a blanket March 2026 migration. Limits apply per method/workspace/app; HTTP 429 includes `Retry-After` seconds. Sources: [history](https://docs.slack.dev/reference/methods/conversations.history/), [replies](https://docs.slack.dev/reference/methods/conversations.replies/), [rate limits](https://docs.slack.dev/apis/web-api/rate-limits/).
- **Authorized history:** Relevant scopes are `channels:history`, `groups:history`, `im:history`, `mpim:history`. History access for bots is restricted to conversations they belong to; user tokens cover their private conversations and public conversations. Thread retrieval requires separate cursor-paginated `conversations.replies` calls. Its current scope table lists both bot and user tokens with all four history scopes; the fetched page does not state the older blanket restriction that channel replies require user tokens. Treat token/channel compatibility as a deployment verification item. Sources: [history access table](https://docs.slack.dev/reference/methods/conversations.history/), [replies scope table](https://docs.slack.dev/reference/methods/conversations.replies/).
- **Exports:** Owners/admins can export public-channel messages and file links on all plans. Business+ owners can apply for all-conversation exports including private channels/DMs; Enterprise owners request separately enabled export tools. These are approval-controlled capabilities, not benefits automatically granted by app installation. Free-plan file-link exports cover only the last 90 days. Source: [export options and roles](https://slack.com/help/articles/201658943-Export-your-workspace-data).
- **Retention:** Free-plan visible message/file history is limited to 90 days; data older than one year is deleted. Retention can be set to 90 days or one year on Free. Paid plans retain data for the workspace lifetime by default but support shorter policies. Retention deletions are permanent. Some configured retention options preserve manually deleted content for approved exports/Discovery; ordinary history access is not equivalent to that capability. Sources: [Free limitations](https://slack.com/help/articles/27204752526611-Feature-limitations-on-the-free-version-of-Slack), [retention](https://slack.com/help/articles/203457187-Customize-data-retention-in-Slack).
- **Unread state:** `last_read`, `unread_count`, and `unread_count_display` are calling-user state supplied by some methods/context, not guaranteed universal fields. `conversations.mark` changes the token owner's cursor and requires membership. A bot's read cursor therefore does not establish a human user's unread state. Sources: [conversation object](https://docs.slack.dev/reference/objects/conversation-object/), [mark](https://docs.slack.dev/reference/methods/conversations.mark/).

## Observed documentation: Discord

- **Message content:** `MESSAGE_CONTENT` is privileged and affects content across APIs, including HTTP. Without configured/approved access, content, embeds, attachments and components are empty and `poll` is omitted. Exceptions include app-authored messages, DMs with the app, app mentions and messages selected for message context-menu commands. Enable required intents in the Developer Portal and include relevant intents when identifying to the Gateway. Current Gateway docs describe privileged-intent review above **10,000 unique users who can see the app**, with annual reapplication; confirm the app's actual review status rather than relying on older server-count guidance. Source: [Gateway intents and review](https://docs.discord.com/developers/events/gateway#message-content-intent).
- **History permissions:** Guild history requires `VIEW_CHANNEL`; without `READ_MESSAGE_HISTORY`, no messages are returned. Voice-channel history additionally needs `CONNECT`. Pages contain 1–100 messages (default 50), newest first; `before`, `after`, `around` are mutually exclusive message-ID boundaries. A successful response does not imply content-intent access. Source: [message resource/history](https://docs.discord.com/developers/resources/message#get-channel-messages).
- **Scope and threads:** Channel permission overwrites affect effective access. Gateway initial guild data includes active threads the current user can view; this is not an exhaustive archived-thread inventory. Sources: [permissions](https://docs.discord.com/developers/topics/permissions), [channel/thread objects](https://docs.discord.com/developers/resources/channel).
- **Unread limitation — bounded finding:** The inspected public channel/history API docs expose latest-message IDs and pagination, but no general per-human unread cursor for a bot integration. Neither a latest-message ID nor an ingestion checkpoint establishes personal read state. This is a limitation of the reviewed documented integration surface, not a claim about Discord's internal client APIs. Sources: [channels](https://docs.discord.com/developers/resources/channel), [history](https://docs.discord.com/developers/resources/message#get-channel-messages).

## Observed documentation: Ragas

| Metric | What it measures / required evidence | Official source |
| --- | --- | --- |
| Faithfulness | Response claims supported by retrieved context; score 0–1. Context-grounded consistency does not independently establish real-world truth. | [Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) |
| Context precision | Whether relevant retrieved chunks rank highly. Current `ContextPrecision` uses a reference answer; response-based utilization/legacy no-reference variants assess a different comparison. | [Context precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) |
| Context recall | Coverage against reference evidence; LLM variant checks reference-answer claims against retrieved contexts. Non-LLM/context-ID variants need reference contexts/IDs. | [Context recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/) |
| Answer/response relevancy | Alignment of response with user input, using generated questions and embedding similarity; explicitly does not assess factual accuracy. | [Response relevancy](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/) |

Current metric pages recommend the `ragas.metrics.collections` API for new projects and label older `SingleTurnSample` metric examples as legacy, with a stated deprecation/removal timeline. Select examples against a pinned release rather than mixing generations. Source: [current and legacy metric APIs](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/).

## Observed documentation: Langfuse

- **Datasets:** Items hold input, optional expected output and metadata; UI/SDK workflows can add items, including from observations. Item add/update/delete/archive creates timestamped dataset versions; fetches default to latest and can select a version. Schema changes are not versioned. Source: [datasets and versioning](https://langfuse.com/docs/evaluation/experiments/datasets).
- **Experiments:** SDK experiments run a task over local data or managed datasets, support per-item evaluators and run-level evaluators, record results/traces, and expose concurrency and metadata controls. Python uses `run_experiment`; JS/TS examples include `dataset.runExperiment` and `langfuse.experiment.run`. Existing generated outputs belong in experiment workflows rather than being mistaken for dataset expected outputs. Sources: [experiments SDK](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk), [datasets](https://langfuse.com/docs/evaluation/experiments/datasets).

## Recommendations for RecallHQ — design judgments, not platform guarantees

1. **Bound history promises.** Show authorized channels, oldest/newest successfully indexed times, missing thread coverage, pending backfill and permission/retention gaps. Scope retrieval and citations to the requesting user's current access; the connector's broader access or possession of an export is not sufficient authorization to disclose every message. Reconcile revocations, edits and deletions in the index and evaluation copies.
2. **Use application-owned catch-up checkpoints.** Keep per-user “last reviewed in RecallHQ” separate from ingestion progress and any verified platform read cursor. Label results “since your last RecallHQ review” or by an explicit time window unless personal platform state is actually available. Do not move platform read cursors merely because content was fetched or summarized.
3. **Budget backfill by app class.** At 15 objects/minute, a full page every permitted minute yields at most 900 objects/hour per restricted method/workspace/app before retries or partial pages (derived upper bound). Thread calls can return parents as well as replies. Use bounded backfill, durable message/time checkpoints, deduplication and `Retry-After`; do not treat pagination cursors as personal unread state or permanent bookmarks.
4. **Use a small, reviewed evaluation set.** Include question, requesting identity/access scope, time cutoff, expected answer/abstention, source message IDs and reference evidence. Cover cross-thread questions, stale decisions, unavailable history, denied channels, deleted sources and unanswerable questions. Keep development and held-out cases separate.
5. **Combine metrics with explicit product checks.** Measure retrieval precision/recall, faithfulness and relevancy separately; add citation validity, access leakage, temporal correctness, abstention, latency and cost. Calibrate LLM judges against human review; high relevancy/faithfulness alone is not sufficient. Wrap Ragas scores as Langfuse custom evaluator results if useful; this is a proposed integration, not one executed here.
6. **Make comparisons reproducible.** Pin dataset version and record corpus snapshot/access scope, schema, prompt, retriever settings, model/judge versions and metric/library versions in experiment metadata. Store only authorized evaluation content; external tracing or judge calls require a separately approved data-processing configuration.
